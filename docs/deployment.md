# Deployment

English | [中文](deployment.zh-CN.md)

The backend listens only on `127.0.0.1`; the HTTPS entry point is a separate layer, and the two ports need not
match. Get the local backend running first, then configure the entry point.

Do not commit real tokens or host paths. `config/projects.json`, `deploy/*.env` and `deploy/*.local` are all
excluded by `.gitignore`.

## 1. Prepare

The service runs as **a non-root Unix user that already has Codex installed and signed in**: Codex reads its
sign-in state and sessions from that user's HOME, and attachments also go through a socket under the same user.
A dedicated service account works too, but then install Codex, sign in and grant project access under that
account; do not share data across accounts by loosening directory permissions.

For attachments, first install the upload service following the deployment notes of the separate
[`ai-remote-upload`](https://github.com/lizzyhague/ai-remote-upload) project. This repository no longer ships its
source or start-up entry points.

Check in that user's login environment (Node.js 24 or later is required):

```bash
id -un; id -gn; printf '%s\n' "$HOME"
node --version
command -v node; command -v codex
```

The runtime user's HOME holds Codex's sign-in and sessions, so do not add restrictions such as
`ProtectHome=true` that would block these directories.

## 2. Install the code and configuration

```bash
git clone https://github.com/lizzyhague/codex-remote.git
cd codex-remote
npm ci --include=dev
npm run typecheck && npm test

cp config/projects.example.json config/projects.json
cp deploy/codex-remote.env.example deploy/codex-remote.env
chmod 600 config/projects.json deploy/codex-remote.env
openssl rand -hex 32
```

Edit `config/projects.json` and replace the example root with real directories on this host; the selectable
projects on the page are the first-level folders under each root. Do not configure `/` or the whole HOME as a
project root.

Edit `deploy/codex-remote.env` and fill in at least:

| Variable | Value |
| --- | --- |
| `CODEX_REMOTE_TOKEN` | The random value generated by `openssl` above, at least 32 characters |
| `CODEX_REMOTE_PORT` | An unused loopback port (defaults to 3000 when unset) |
| `CODEX_REMOTE_PROJECTS_CONFIG` | Absolute path of `config/projects.json` |
| `CODEX_BIN` | The absolute path returned by `command -v codex` |

`CODEX_REMOTE_ALLOWED_ORIGINS` is usually left empty; fill in full origins only when the reverse proxy does not
preserve `Host` / `X-Forwarded-Host`.

## 3a. Linux + systemd

```bash
cp deploy/codex-remote.service.example deploy/codex-remote.service.local
```

Replace the placeholders in the local copy: `__RUN_USER__`, `__RUN_GROUP__`, `__RUN_HOME__`, `__APP_DIR__` (the
repository root), `__ENV_FILE__`, `__NODE_BIN__`, `__RUNTIME_PATH__` (a full PATH containing Node and Codex). The
example uses `Wants`/`After` to order start-up after `ai-remote-upload.service` without tying this service's
life to the upload service.

```bash
grep -n '__[A-Z_]*__' deploy/*.service.local   # should print nothing
sudo install -m 0644 deploy/codex-remote.service.local /etc/systemd/system/codex-remote.service
sudo systemctl daemon-reload
sudo systemctl enable --now codex-remote.service
curl --fail --show-error http://127.0.0.1:3000/healthz
```

On an existing host that should keep its own `codex-remote.service`, you can install only
`deploy/codex-remote-upload.conf` as `/etc/systemd/system/codex-remote.service.d/20-ai-remote-upload.conf` and
then `daemon-reload`. It uses `Wants` rather than `Requires`: a broken shared service only makes attachments
fail and does not block plain-text start-up. The upload service itself is still installed from the
`ai-remote-upload` repository.

## 3b. macOS + launchd

Use a system LaunchDaemon so the service does not depend on a graphical login; `UserName` is still the ordinary
user above who is signed in to Codex. The upload service's plist lives in the `ai-remote-upload` repository, not
here.

```bash
cp deploy/launchd/codex-remote.plist.example deploy/launchd/codex-remote.plist.local
mkdir -p "$HOME/Library/Logs/codex-remote" && chmod 700 "$HOME/Library/Logs/codex-remote"
```

There are two more placeholders than for systemd: `__REMOTE_SERVICE_LABEL__` (a different launchd label for each
instance) and `__LOG_DIR__`. The file name, the plist's `Label` and the `launchctl` command must all agree; the
`io.example.*` below is only an example.

```bash
grep -n '__[A-Z_]*__' deploy/launchd/*.plist.local   # should print nothing
plutil -lint deploy/launchd/*.plist.local
sudo install -o root -g wheel -m 0644 deploy/launchd/codex-remote.plist.local \
  /Library/LaunchDaemons/io.example.codex-remote.plist
sudo launchctl bootstrap system /Library/LaunchDaemons/io.example.codex-remote.plist
curl --fail --show-error http://127.0.0.1:3000/healthz
```

This repository does not set a start-up order for the upload service; when the shared service is not up, only
attachments fail.

If a proxy is needed, put `HTTPS_PROXY` and the like in `deploy/codex-remote.env`, and use `NO_PROXY` to keep
`127.0.0.1`, `localhost` and private-network entry points direct.

Do not move on to the entry point until the health check passes.

## 4a. Tailscale Serve (tailnet only)

```bash
tailscale serve status                                    # check what is already in use
tailscale serve --bg --https=8443 http://127.0.0.1:3000
tailscale serve status
```

Choose the port that suits this host. The first time, you may need to enable tailnet HTTPS in the browser. Then
open the address shown in the status from another tailnet device, sign in and send a test message.

Tailscale identity governs network access and the application token governs sign-in; the two layers are
independent. Do not switch `serve` to `funnel` and keep treating it as private — that is a public entry point.

## 4b. Public HTTPS

Public addresses are scanned constantly. Understand before taking this path: a leaked token lets someone else
drive your Codex, and the application token is a long-lived shared credential, not a user identity system.

Minimum requirements: run as a non-root user, use a high-entropy dedicated token, open only 80/443 while the
backend stays on loopback, have valid HTTPS, keep project roots as narrow as possible, and set connection and
request limits at the proxy.

Minimal Caddy configuration:

```caddyfile
codex.example.com {
    reverse_proxy 127.0.0.1:3000
}
```

```bash
caddy validate --config /etc/caddy/Caddyfile
systemctl reload caddy
curl https://codex.example.com/healthz
```

Another reverse proxy must meet all of these: forward the WebSocket Upgrade correctly, preserve the original
`Host` or set `X-Forwarded-Host` correctly, and not let outside clients forge trusted proxy headers.

Before going live, confirm in a browser: HTTP redirects to HTTPS, a wrong token cannot sign in, the right token
loads the project list, the WebSocket is `wss://`, and the backend's loopback port is unreachable from the
public address.

## 5. Frontend updates

There is no separate frontend build command. Before it starts listening, the service reads the whole frontend,
generates versioned addresses for scripts and styles, and stores them in `public/.web-assets/`. The runtime
account must be able to write that directory; it is ignored by Git. Later changes to the working tree do not
affect the running process, and frontend and backend switch together on restart. When the frontend is incomplete
(a script referenced by the page or a module is missing), the service refuses to start rather than serve half a
page.

`.web-assets/` keeps the current version and the old versions of the last two start-ups; older ones are deleted
automatically at start-up, and pages already open on an old version can still fetch its assets meanwhile. When
deploying new code, do not empty this directory by hand or commit it.

Frontend files still go through the HTTP static asset allowlist. Register new scripts or styles in the allowlist
in `src/server/http-server.ts`; editing existing frontend files needs no manual version bump. Update steps and
rolling back after a failed check are in [Operations](operations.md#updates).

When online, an ordinary refresh fetches the current page and its matching scripts and styles, without relying
on an update prompt or a service worker takeover. On a phone, pull down at the top of the chat list or session
list, or on a blank part of the title bar, and let go when "Release to refresh" appears. The page never reloads
itself because of a service worker update. Offline, the most recently fully cached page is used; sessions still
need a connection. The browser cache keeps only the scripts and styles of the current offline page and the
previous one; while a new version has not downloaded completely, the old offline page and its assets are left
untouched.

## 6. Several hosts

The recommended pattern is "same version, independent instances": the source may come from the same commit, but
token, port, entry point, project allowlist, state files, upload directory and socket are separate on each host,
with no shared running workers or databases. Do not use file sync tools to write SQLite, attachment directories
or Codex session directories on two machines at once.

The simplest migration leaves history behind: install the same version on the new host, sign in to Codex there,
configure its own allowlist and entry point, and decide whether to stop the old instance after the new one
passes its checks.
