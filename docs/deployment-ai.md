# AI 部署与交接规范

## 文档用途

本文是给协助用户部署 Codex Remote 的 AI 阅读的执行规范。目标用户可能不熟悉代码、
Linux、systemd、Tailscale 或反向代理，因此 AI 必须把事实、推测、建议和执行结果
分开说明，不能让用户根据一串没有解释的命令自行判断风险。

本文中的“必须”和“不得”是部署约束，不是可选建议。用户对部署方式和主机用途的
亲口说明优先；信息不足时先询问，不得按“常见环境”代替用户做决定。

## 阅读顺序

开始部署前，AI 必须按顺序阅读：

1. 仓库根目录的 `README.md`；
2. 本文；
3. 用户选择的 [Tailscale 私网部署](deployment-tailscale.md) 或
   [公网 HTTPS 部署](deployment-public.md)；
4. [运维说明](operations.md)；
5. [安全策略](../SECURITY.md)。

需要解释实现行为时再阅读 [架构说明](architecture.md) 和源码。示例配置只是模板；
实际路径、账户、二进制位置和网络入口必须以目标主机的检查结果为准。

项目最初针对 Codex CLI `0.147.0` 开发和测试。目标主机使用其它版本时，AI 必须指出
版本差异风险，运行类型检查和测试，并把浏览器验收列为必要步骤，不能把实验 App
Server 接口当成跨版本稳定保证。

## 不得突破的边界

无论选择哪种部署路径，都必须保持以下边界：

- 这是单用户、自托管工具，不得包装成公开注册或多人账户服务；
- Node.js 服务只监听 `127.0.0.1`，不得改成 `0.0.0.0`，不得直接暴露 `8787`；
- 远程访问必须使用 HTTPS；明文 HTTP 只允许本机回环健康检查；
- 必须保留至少 32 字符的高熵应用令牌，不得因为已有网络身份层就删除令牌；
- 应使用专用的非 root 系统账户，不得为了省事让服务以 root 运行；
- 项目根目录应尽量窄，不得把 `/`、整个用户主目录或秘密集合配置成项目根目录；
- 不得静默启用 full access；最终文件和命令权限由服务账户与 Codex 权限共同决定；
- 不得把真实令牌、Codex 凭证、私钥或会话内容写进 Git、AI 对话或公开 Issue；
- 项目路径和日志只在当前私密部署对话确实需要时最小化展示，不得复制到公开报告；
- 不得用 `pkill codex` 等宽泛命令处理 writer 或进程故障。

项目白名单只限制网页可以选择的工作目录和可恢复会话，不是文件系统沙箱。应用令牌
泄露后，攻击者能做什么取决于服务账户权限、白名单范围和当前 Codex 权限 profile。

## 第一阶段：只读检查

AI 的第一阶段只能读取状态，不得安装软件、创建账户、改文件、启动或停止服务，也
不得更改防火墙、DNS、Tailscale、反向代理或 Codex 配置。

至少需要确认：

- 用户明确选择 Tailscale 私网还是公网 HTTPS；没有选择时只说明两者差异并询问；
- 操作系统、当前账户和用户是否拥有管理员权限；
- 仓库准备放在哪个绝对路径，当前目录是否已有文件或未提交改动；
- Node.js、npm 和 Codex CLI 的实际路径及版本；
- `codex app-server --stdio` 是否可用；
- 准备运行服务的账户，以及该账户是否已经登录 Codex；
- 允许访问的项目根目录，及服务账户是否确实需要读写它们；
- `8787` 是否已被占用，现有服务是否只监听回环地址；
- 主机上已有的 systemd 单元、Tailscale Serve、Caddy、Nginx、防火墙和云安全组状态；
- 公网部署需要的域名、DNS 和 `80/443` 占用情况；
- 真实配置或日志中是否可能包含不应复制到聊天里的秘密。

声称某个命令不存在前必须实际检查其路径和版本。检查结果不完整时，AI 应说明缺少
什么以及为什么需要它，不得根据示例中的 `/opt/codex-remote`、`/usr/bin/node`、
`/usr/local/bin/codex`、`/srv/projects` 等路径猜测。

## 第二阶段：提出方案并等待确认

只读检查完成后，AI 必须先向用户报告：

1. 已确认的环境事实；
2. 仍然不确定或需要用户选择的事项；
3. 准备采用的部署路径及理由；
4. 准备执行的命令；
5. 准备新增或修改的文件、服务和网络资源；
6. 哪些步骤会中断现有连接或任务；
7. 哪些命令需要 `sudo` 或其它管理员权限；
8. 验证方法和失败时的停止点。

修改用户的文件、系统或服务前必须取得明确同意。需要 `sudo` 的操作必须单独说明
用途和影响；用户只同意普通文件修改，不代表同时同意管理员操作。

如果已选路径遇到阻碍，先报告问题并询问用户。不得未经确认改用公网入口、容器、
其它反向代理、其它账户或其它安装目录。

## 第三阶段：分段执行

用户确认后也应分段执行，每段完成后先验证结果，再进入下一段。

### 1. 准备源码和依赖

- 确认仓库来源、分支和工作区状态；
- 使用 Node.js 24 或更新版本；
- 运行 `npm ci`、`npm run typecheck` 和 `npm test`；
- 不在包含重要文件的正式项目上运行真实 App Server smoke 测试；
- 发现测试失败时先解释，不得通过关闭检查掩盖错误。

### 2. 准备服务身份

- 优先使用专用的非 root 账户；
- 核对该账户的 `HOME`、Node.js、Codex CLI 和项目访问权限；
- Codex 登录必须在最终服务账户身份下完成；
- 需要用户进行交互式登录时，让用户直接在可信终端操作，不要索要或转述凭证；
- 不得照搬会阻断 Codex 登录、会话或配置目录的 systemd 隔离选项。

### 3. 准备配置和秘密

- 在目标主机生成独立随机令牌，不在输出中回显完整值；
- 环境文件权限应为 `600`，并由合适的账户或管理员持有；
- `config/projects.json` 或系统级项目配置只列用户确认的窄范围根目录；
- 根据实际结果填写 `User`、`Group`、`HOME`、`WorkingDirectory`、`ExecStart`、
  `CODEX_BIN` 和配置文件路径；
- 确认真实环境文件和项目配置已被 Git 忽略；
- 不得把令牌放在 shell 历史、命令行参数、截图或部署总结中。

### 4. 建立常驻服务

- 把 `deploy/codex-remote.service` 当模板，不得未经核对直接复制启动；
- 启动前再次展示最终单元中的身份、目录和二进制路径；
- 按 [运维说明](operations.md) 安装、启动并检查 systemd 服务；
- 服务反复重启时先检查日志和 App Server stderr，不得只反复重启。

### 5. 建立唯一的 HTTPS 入口

- 用户选择私网时按 [Tailscale 私网部署](deployment-tailscale.md) 执行；
- 用户明确接受公网风险时才按 [公网 HTTPS 部署](deployment-public.md) 执行；
- 不得同时留下用户不知情的多套入口；
- 只有日志证明代理确实改写 Host 时，才设置精确的
  `CODEX_REMOTE_ALLOWED_ORIGINS`；不得使用宽泛通配符；
- 公网部署应在防火墙、云安全组或入口代理层限制请求，并优先增加独立身份层。

## 第四阶段：完成验证

至少完成以下验证后，才能说“部署完成”：

1. `npm run typecheck` 和 `npm test` 成功；
2. systemd 单元为 `enabled` 和 `active`；
3. `curl http://127.0.0.1:8787/healthz` 成功；
4. 监听检查显示后端只绑定 `127.0.0.1:8787`；
5. 实际 HTTPS 地址的 `/healthz` 成功；
6. 浏览器通过 `https://` 打开，WebSocket 使用 `wss://`；
7. 错误令牌无法登录，正确令牌可以加载预期项目；
8. 配置中没有意外的 full access 或过宽项目根目录；
9. 公网部署时，从公网不能直接访问 `8787`；
10. 日志中没有持续重启、Origin 拒绝或敏感信息泄露。

`/healthz` 只证明网页后端响应，不单独证明入口安全、令牌正确、项目权限正确或实际
浏览器流程可用。无法完成某项验证时，AI 必须明确标记“未验证”，不能用“应该可以”
代替结果。

## 第五阶段：必须完成的用户交接

部署完成后，AI 必须用普通用户能理解的语言主动说明以下内容。不要只回复“服务已
启动”或丢下一组命令。

### 部署结果

- 实际访问地址，以及它是 tailnet 私网地址还是公网地址；
- 服务当前是否启用并运行；
- 服务使用的系统账户、代码目录和配置位置；
- 项目白名单的大致范围，不在公开文字中泄露不必要的绝对路径；
- 已完成、失败和未完成的验证；
- 查看状态、查看日志、重启和更新所需的准确命令；
- 哪些维护操作需要管理员权限，哪些操作会中断任务。

### 安全边界

- 这是单用户、共享令牌系统。不同浏览器不是不同账户，不能用它给互不信任的人使用；
- 令牌会保存在浏览器 `localStorage`。不要在共享或不可信设备上保存令牌；
- 怀疑令牌泄露时，要生成新令牌、更新服务环境、重启服务，并清除浏览器旧值；
- 项目白名单不是沙箱。Codex 最终权限取决于服务账户和当前权限 profile；
- full access 会扩大误操作和令牌泄露影响，尤其不适合作为公网实例的默认值；
- `8787` 必须始终只在回环地址监听，远程访问只能经过受控 HTTPS 入口；
- 公网地址会持续面对扫描和恶意流量；应用令牌不能代替 MFA、分用户授权或审计。

### 多终端连接行为

- 手机、电脑和多个标签页共用同一个应用身份；已连接设备可能看到同一会话的新消息
  和 AI 输出，不应把观察端当成隐私隔离；
- 同一项目同时只运行一个任务；已接受的新消息会持久化并排队，不能并发修改同一
  原生会话；
- 页面关闭、锁屏、切换网络或 WebSocket 断线不会直接中断已接受任务。重新连接并
  打开该会话后，页面会重放已经保存的输出和最终状态；
- 所有已认证设备都会收到待处理的权限或交互请求。手动权限模式下，全部设备离线
  超过宽限时间仍无人处理时，后端拒绝该请求并中断整轮；Full access 下可授权请求
  可以自动通过，但用户输入和 MCP 登录不能由后端猜测；
- 每个活动会话由独立 App Server Worker 持有 writer；任务完成且队列为空后立即
  退出。只停在项目或会话列表不会持有会话 writer；
- 服务重启会断开所有网页连接并中断正在执行或等待交互的 Worker；尚未启动的排队
  消息会保留，并在服务恢复和资源允许时继续调度；
- 本机 Codex CLI 要接管某个正在执行的会话时，应先在网页停止该任务并等待 Worker
  退出。若无法正常释放，再按运维文档有序停止整个 Codex Remote 服务；
- 不要用 `pkill codex` 解决 active writer。必要时按运维文档停止 Codex Remote
  服务，并先说明这会中断所有网页任务。

### 日常维护

- 更新前确认没有活动任务；更新后运行依赖安装、类型检查、测试、服务重启和健康检查；
- 升级 Codex CLI 后要重新测试并做浏览器验收，因为生成类型和实验接口与版本有关；
- 故障排查从回环健康检查、systemd、HTTPS 入口、Origin/Host、浏览器缓存逐层进行；
- 不要把真实令牌、会话内容或含私人路径的日志粘贴到公开 Issue。

## 建议的交接格式

AI 可以使用下面的结构汇报，但每一项必须填入实际检查结果：

```text
部署结果
- 访问地址：
- 网络范围：Tailscale 私网 / 公网 HTTPS
- 服务状态：
- 服务账户与代码目录：
- 已完成验证：
- 未完成或需要用户处理：

你现在需要知道
- 安全边界：
- 令牌保存与轮换：
- 项目与 Codex 权限：
- 多终端控制规则：
- 本机 CLI 接管会话的方法：
- 更新、日志和重启命令：
```

部署过程中的命令输出与交接结论不一致时，以实际结果为准，并把差异明确告诉用户。
